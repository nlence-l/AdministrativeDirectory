# Audit Policy & SIEM — Reference

This document records the security auditing configured for the project (the
"SIEM" logging layer) and the Windows Event IDs each category produces. It is the
map between *what is audited* and *what the analysis scripts query*.

## What "SIEM" means here

Active Directory has no built-in SIEM — SIEM (Security Information and Event
Management) is a separate product category (Splunk, Sentinel, Wazuh, etc.). What
Windows provides is the *logging layer* a SIEM consumes: the Security event log,
audit policy to control what gets logged, and tools to query it. This project
implements that foundation natively — auditing to generate the events, and
PowerShell scripts to analyze them — which is the collection-and-analysis core a
SIEM is built on.

## How auditing works

An event only appears in the Security log if its audit category is enabled. Most
categories are off by default. Auditing is configured through **Advanced Audit
Policy Configuration** in `GPO-Audit` (Computer Configuration → Windows Settings
→ Security Settings), linked to the Domain Controllers OU.

For file/folder auditing there is a second requirement: beyond enabling the
category, each folder must carry a **SACL** (an auditing entry on the folder's
Advanced Security → Auditing tab). Without both the category and the SACL, no
file-access events are produced.

## Configured audit subcategories

Domolia's seven requested activities, plus bonus additions for fuller SIEM
coverage. All set to **Success and Failure** so that failed attempts (often the
security-relevant ones) are captured, not just successes.

| Category | Subcategory | Setting | Source |
|----------|-------------|---------|--------|
| Account Management | Computer Account Management | Success + Failure | Required |
| Account Management | Distribution Group Management | Success + Failure | Required |
| Account Management | Security Group Management | Success + Failure | Required |
| Account Management | User Account Management | Success + Failure | Required |
| DS Access | Directory Service Access | Success + Failure | Required |
| Logon/Logoff | Logon | Success + Failure | Required |
| Logon/Logoff | Logoff | Success + Failure | Required |
| Object Access | File System | Success + Failure | Bonus / needed for folder script |
| Detailed Tracking | Process Creation | Success + Failure | Bonus (SIEM-necessary log) |

Verify the applied state with:

```
auditpol /get /category:*
```

## Script → Event mapping

Which analysis script reads which events (see `scripts/siem/`).

| Script | Reads | Reports |
|--------|-------|---------|
| `Get-ConnectedUsers.ps1` | 4624 | Users logged on within a time window |
| `Get-UserEvents.ps1` | all (filtered by user) | Every event concerning one user |
| `Get-FolderActivity.ps1` | 4663, 4660 | Access / modification on a folder |
| `Get-UserIPs.ps1` | 4624 (opt. 4625) | Source IPs used by each user |
| `Get-SecurityIncidents.ps1` | 4625, 4740, 4726, 1102, 4719, … | Flagged security incidents + brute-force |
| `Invoke-IncidentResponse.ps1` | 4625 | Auto-disables accounts on persistent failures |
| `Set-AuditPolicy.ps1` | — | Enables/disables audit subcategories |

## Notes on volume

File System auditing (4663) and Process Creation (4688) are high-volume — every
file read and every process launch generates an event, so the Security log fills
quickly. For a focused folder-modification view, a SACL can audit only
Write/Delete rather than Read, reducing noise while still capturing changes.
